Explore the GitHub interface

What lives inside a GitHub repository?

Repository

The project container: code, history, branches, and collaboration settings.

README

The front page: what the project does, how to install and run it, and how to contribute.

Issues

A task or problem tracker: bugs, feature requests, questions, and assigned work.

Pull Requests

A proposal to bring changes from one branch into another, with discussion and review.

Actions

Automated jobs such as running tests or deploying after a change.

Releases

Named project versions shared with users, often with notes and downloadable files.

Other useful areas: Projects (organise tasks), Wiki (longer documentation), Insights (activity), and Settings (permissions and configuration).
Repository visibility

Public vs private repositories

Public

Anyone can view the code and history.

  • Good for open-source projects, portfolios, and public demos.
  • Others can inspect and may fork it.
  • Only authorised collaborators can push directly.

Private

Access is limited to you and people you invite.

  • Good for work in progress or restricted source code.
  • Useful for team projects before public release.
  • Members need appropriate permissions.
Important: private does not mean encrypted storage for secrets. If a key or password is committed, treat it as exposed: revoke/rotate it. Removing it in a later commit does not erase the old history.
Phase 1 · Setup

Install Git and introduce yourself

1. Install and verify

git --version

Download Git from git-scm.com/downloads.

2. Configure your identity

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

What do these settings do?

  • user.name: name attached to your commits.
  • user.email: email attached to your commits.
  • init.defaultBranch: branch name used when starting a new repository.
  • --global: applies to your user account on this computer.
git config --global --list
A commit is not automatically uploaded to GitHub. At this point, everything is still on your computer.

The core Git mental model

Three places your changes move through

Working directory

Your project files. You edit here.

EDIT
→

Staging area

Changes selected for the next save point.

git add
→

Local repository

Committed project snapshots and history.

git commit

Why stage first?

You may have edited five files but only want two in the next commit. Staging lets you choose exactly what goes into that snapshot.

What is a commit?

A named snapshot of staged changes, linked to its parent history. It is not just a normal save button.

Remember: edit → add → commit. Push comes later, when you want to send commits to a remote repository.

Good habits

Make commits that tell a story

Good commit messages

  • Add email validation to signup form
  • Fix null response in patient search
  • Document local development setup
  • Add API health-check endpoint

Weak commit messages

  • update
  • final version
  • changes
  • working now

They do not help teammates understand the project history.

A useful rule: one commit should represent one understandable piece of work. Commit often, but keep each commit focused.
Keep the repository clean

What should not enter Git?

Example .gitignore

# Dependencies
node_modules/

# Environment variables and secrets
.env
.env.*

# Build output
dist/
build/
coverage/

# Local editor / OS files
.DS_Store
.vscode/

Why ignore these?

  • Dependencies can be reinstalled from package files.
  • Build output can usually be regenerated.
  • Local editor settings may differ by developer.
  • Secrets must not be shared through source control.
Warning: adding a filename to .gitignore does not untrack it if Git already tracks it.

Branch commands

Create, switch, merge, clean up

git branch                         # list local branches
git switch -c feature/login        # create + switch
# edit and commit your feature
git switch main                    # return to target branch
git merge feature/login            # bring feature into main
git branch -d feature/login        # delete merged branch

Create

git switch -c name

Starts a new line of work from your current commit.

Switch

git switch main

Moves your working directory to another branch.

Merge

git merge name

Combines the named branch into the branch you are currently on.

The order matters: switch to the branch that should receive the work, then merge the feature branch into it.
When Git needs a human decision

Merge conflicts are not project failures

What a conflict looks like

<<<<<<< HEAD
const title = "Patient Dashboard";
=======
const title = "Health Records";
>>>>>>> feature/records

Git is showing two competing edits to the same section.

How to resolve it

  1. Open the conflicted file.
  2. Choose or combine the correct lines.
  3. Delete conflict markers.
  4. Save the file.
  5. Run git add filename.
  6. Complete the merge commit if prompted.
Talk to the other developer if the correct answer is unclear. Git can detect overlapping edits; it cannot understand your product requirements.

Remote

A saved name and URL pointing to another copy of the repository. The common name is origin.

git remote -v

Why connect?

Back up work, share code, review contributions, and coordinate with other developers.

Local commits remain local until pushed to a remote.

The sync commands

Clone · Fetch · Pull · Push

CommandPlain meaningDirection
git clone URLDownload a repository and set it up locallyGitHub → laptop
git fetchCheck/download remote updates without integrating themGitHub → local metadata
git pullFetch and integrate remote updates into current branchGitHub → current branch
git pushSend your local commits to the remoteLaptop → GitHub
Before starting work, a safe habit is to switch to the correct branch and pull the latest shared changes. Before pushing, check status and commit history.
First upload · Existing local project

Connect your project to GitHub

  1. Create a new repository on GitHub. Choose public or private. For an existing local project, leave README/.gitignore/license unchecked to avoid an unrelated initial commit.
  2. Copy the repository URL, then run:
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git remote -v
git push -u origin main

What is -u?

It sets the upstream branch. Later you can usually run git push and git pull without repeating the remote and branch.

Authentication

Use GitHub's browser sign-in / credential manager or configure SSH keys. GitHub account passwords are not accepted for ordinary Git HTTPS authentication.

Organising contributions

Issues, forks, and open source

GitHub Issues

Think of an Issue as a work ticket.

  • Bug: login button does nothing.
  • Feature: add a patient search filter.
  • Task: write API setup instructions.

Use labels, assignees, milestones, and checklists to clarify ownership and progress.

Forking

A fork is your GitHub-side copy of another person's repository.

  1. Fork the project.
  2. Clone your fork.
  3. Create a branch and make changes.
  4. Push to your fork.
  5. Open a Pull Request to the original project.
Before contributing, read the project's README and CONTRIBUTING guide. Follow its code style, tests, and communication expectations.
Phase 4 · Safety nets

Undoing mistakes without panic

CommandWhat it doesRisk / use
git restore fileDiscard unstaged edits in a fileDestructive to those edits
git restore --staged fileUnstage a file but keep its editsUsually safe
git revert COMMITCreate a new commit that reverses an earlier commitGood for shared history
git reset --soft HEAD~1Move branch back one commit, keep changes stagedChanges history
git reflogShow recent movements of HEAD/branch refsCan help recover lost work
Do not run commands you do not understand, especially reset --hard or force-push on shared branches. Ask what will be lost first.
More useful workflows

Stash, rebase, and squash

Stash

Temporarily put unfinished changes aside.

git stash
git switch main
git stash pop

Like putting your current desk work in a drawer.

Rebase

Replay your branch commits on top of a newer base.

git switch feature/login
git rebase main

Can make history more linear; may require conflict resolution.

Squash

Combine several small commits into one meaningful commit, often during PR merge.

git rebase -i HEAD~3

Useful for tidying noisy history before sharing.

Team rule: do not rewrite shared history casually. Prefer a normal merge or ask the team before rebasing published commits.
GitHub extras

Automation and publishing

GitHub Actions

Automates repeated project checks when code changes.

Code pushed
    ↓
Install dependencies
    ↓
Run lint + tests
    ↓
Build application
    ↓
Report pass / fail

Useful for catching errors before merging.

GitHub Pages

Publishes static websites from a repository.

  • Portfolio sites
  • Project documentation
  • Static demos and club resources

For a backend API or full-stack app, use a suitable application host instead.

Responsible collaboration

Protect the project and the people in it

Never commit

  • Passwords, API keys, tokens, SSH private keys.
  • Real patient records or identifiable health data.
  • Production database backups.
  • Private documents without permission.

Do instead

  • Use .env and secret storage.
  • Commit an .env.example with placeholder values.
  • Use synthetic/sample data for demos.
  • Enable 2FA and review collaborator access.
  • Protect main with Pull Requests and checks.
If a secret enters Git history, revoke or rotate it immediately. Deleting the line in a later commit does not make the old secret safe.
